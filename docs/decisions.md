# Decision Log

Engineering decisions and live-verified service behaviors, recorded as they
were made. Entries capture what we verified against installed libraries and
the running services — many were found the hard way, so read this before
assuming a service behaves the way its docs suggest.

| # | Date | Decision | Detail |

| D-28 | 2026-09-02 | Region is an explicit context flag (`-c region=…`), like modelId | Live finding during the multi-region deploy test: the CDK CLI computes the target region from the profile/`AWS_REGION` and OVERWRITES any inherited `CDK_DEFAULT_REGION` when spawning the app — a deploy run with `CDK_DEFAULT_REGION=us-west-2` silently landed in the profile's default region (us-east-1), where the workload secrets didn't exist, surfacing as a misleading `ApiKeyCredentialProvider` "Secrets Manager can't find the specified secret" create failure. Fix follows D-10's explicit-decision stance: `bin/` resolves `-c region` context first (then the CLI-populated `CDK_DEFAULT_REGION`, then the ap-southeast-2 default), and the stack's declared env is authoritative for the deploy target regardless of profile region |
| D-27 | 2026-09-01 | Every harness execution role gets runtime observability permissions | Live find: CloudWatch reported "log group does not exist" for `/aws/bedrock-agentcore/runtimes/harness_planner-*-DEFAULT` after successful invocations — AgentCore Runtime creates and writes its runtime log group THROUGH THE HARNESS EXECUTION ROLE, and `HarnessAgent`'s derived role granted no logs/xray/metrics actions at all. The role now matches the service's reference execution-role policy: `logs:CreateLogGroup`/`DescribeLogGroups` + `CreateLogStream`/`PutLogEvents`/`DescribeLogStreams` scoped to `/aws/bedrock-agentcore/runtimes/*`, X-Ray segment/telemetry/sampling actions, and `cloudwatch:PutMetricData` conditioned to the `bedrock-agentcore` namespace. Log groups appear lazily on the first invocation AFTER the role update — a fresh deploy with zero runs having no log group is normal |
| D-26 | 2026-08-31 | Python developer surface: agents in YAML, tools in Python, feature APIs via additionalRoutes | Customer teams build Bedrock agents in Python + React frontends; the platform's editable surfaces now match that shape without rewriting internals. (1) `loadWorkloadManifest` (constructs): agents defined in `workload.yaml` — snippets for shared prompt blocks, symbolic `gateway:`/`browser:` refs resolved by the stack — validated by the SAME zod HarnessConfigSchema at synth; the example workload's agents/*.ts deleted after a byte-identical round-trip check (deploy is a harness no-op). (2) `tools-py/`: `tool_result.py` mirrors createToolHandler; stdlib+boto3-only handlers need no bundling (Code.fromAsset, done); reference tool `currency_rates` (keyless ECB rates via frankfurter.dev) registered as its own Python 3.13 gateway target and granted to data_analysis. Schema JSON lives next to the handler. (3) `AgenticApi.additionalRoutes`: customer Python Lambdas mount on the same HTTP API behind the same JWT authorizer; reserved prefixes (/workflows, /runs, /settings, /plan-drafts) rejected at synth. UI features remain TypeScript end-to-end (browser + shared plan-schema types) — documented boundary in docs/python-developers.md |
| D-25 | 2026-08-31 | Independent per-tool gateway targets; vendor-hosted MCP servers federate directly | Tool layer restructured from one shared research-tools Lambda to one gateway target per tool: (1) vendors that host an MCP server plug in natively via the new `GatewayMcpServerTarget` construct (`McpServerTargetConfiguration` + `ApiKeyCredentialProvider` token-vault auth, header or query-param injection) — Tavily federates from `https://mcp.tavily.com/mcp/` with the key as the `tavilyApiKey` query parameter, exposing tavily_search plus its sibling tools (extract/map/crawl/research) with no Lambda; (2) executor tools (news/financial/social — no vendor MCP) each ship as their own Lambda via `createToolHandler`, with IAM scoped to exactly one secret (the shared `marketing-workflow/*` wildcard grant is gone). Live-verified: gateway tools/list serves all four targets; the Tavily target lists tools even with a placeholder key (validation happens at call time). Caveats: the credential provider copies the key at deploy — rotating the secret later requires updating the provider too; `SecretValue.secretsManager` means the tavily secret must exist before deploy. patent_search keeps its own handler bundle, held back for the live build-along demo |
| D-24 | 2026-08-31 | Harness `allowedTools` must be `['*']` — any concrete list disables ALL tools | Live incident (run b04904cb): worker outputs contained narrated pseudo-tool-calls; the tools Lambda's log group showed ZERO invocations since stack creation — no workflow run had ever executed a real tool. Root cause isolated by A/B harness tests: with `allowedTools` unset, gateway tools fire (toolUse events, Lambda invoked); with ANY concrete value — bare names (`tavily_search`), target-prefixed (`<target>___<tool>`), wrapper-qualified (`gateway___<target>___<tool>`), or `[]` — the runtime exposes zero tools and the model fabricates results. The field is also sticky: once set it cannot be cleared by omission on update; `['*']` is the only value that both exposes tools and is update-safe in place. `HarnessAgent` now always emits `allowedTools: ['*']` for tool-bearing agents; per-tool scoping remains at the worker-catalog/plan-validation level (already the enforced layer). Separately confirmed: no `marketing-workflow/*` secrets exist in the demo account, so executors return "API key not configured" until real keys are added |
| D-23 | 2026-08-31 | Enforce the D-22 "no absolute dates in task prompts" rule in validation, not just instruction | Live finding: a fresh example-workload draft (`/workflows/4be2e30c-...`) had every task prompt opened with "Today's date is Monday, August 31, 2026." — planner rule 7 asks the model not to do this but nothing checked compliance. `validatePlanAgainstCatalog` now rejects literal calendar dates (`Month D, YYYY`, `D Month YYYY`, `Weekday, Month D`, ISO `YYYY-MM-DD`) in every `task.prompt` and `report.instructions`, feeding the same corrective-retry loop (`PlannerClient`) and savePlan 422 path as the D-14 invented-tool/model checks. Runtime date injection (D-22) is unchanged and remains correct — this closes the authoring-time gap only |

| D-20 | 2026-08-28 | Per-workflow failure policy (contain / fail-fast / retry-run ≤3) + Bedrock model-id verification | Live incident: an invalid model id failed every task as harness RuntimeClientError (ValidationException on ConverseStream, 424) while the run kept executing under failure containment — the D-18 `Model` field itself was accepted, confirming the SF PascalCase convention. Two fixes: (1) `failurePolicy` on the workflow (default `contain` keeps the containment behavior), editable by the owner: `fail-fast` — RecordTaskFailure returns a policy verdict from the run record and a Choice raises `FailFastStop`, failing the wave into the finalize catch (run failed, no report); `retry-run` — new `EvaluateRunHealth` state after each full wave pass resets failed+skipped tasks to pending (succeeded artifacts kept), bumps the run's `attempts` (conditional update; crash-safe resume via the pending-tasks check) and loops the waves up to `maxAttempts` (≤3) before falling back to contain. Policy is stamped onto the run record at PrepareRun so mid-run edits never change in-flight behavior. (2) PUT /settings/org verifies every catalog modelId against `ListFoundationModels` + `ListInferenceProfiles` (ids and ARNs, paginated) in-region; unknown ids → 400 with the offending list; Bedrock listing outage → fail-open with `verified:false`. Router gains the two list-only Bedrock IAM actions |
